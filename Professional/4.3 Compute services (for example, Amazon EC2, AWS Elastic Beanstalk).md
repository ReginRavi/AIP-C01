# Task 4.3: Determine a New Architecture for Existing Workloads

## Compute Services

The two services you listed are:

1. Amazon EC2
2. AWS Elastic Beanstalk

The key SAP-C02 concept is not memorizing features. It is deciding how much infrastructure management the workload requires.

A useful mental model is:

```text
More infrastructure control
        ↓
     Amazon EC2
        ↓
   Elastic Beanstalk
        ↓
   More AWS-managed
        ↓

More control ←──────────────→ Less operational effort
More management ←───────────→ More automation
More flexibility ←───────────→ More opinionated platform
```

---

# 1. Amazon EC2

## Why did EC2 exist in the first place?

EC2 exists to solve one fundamental problem:

"How do I get virtual servers in AWS without buying and maintaining physical servers?"

Before cloud computing, you typically needed to:

```text
Buy physical server
        ↓
Install OS
        ↓
Configure network
        ↓
Install applications
        ↓
Maintain hardware
        ↓
Replace failed hardware
```

EC2 moves the physical infrastructure responsibility to AWS.

You still control the virtual machine.

```text
AWS manages
├── Physical hardware
├── Data center
├── Power
├── Networking infrastructure
└── Hypervisor

You manage
├── OS
├── Patching
├── Runtime
├── Application
├── Security configuration
└── Scaling configuration
```

This distinction is extremely important for SAP-C02.

---

# 2. What problem does EC2 solve?

EC2 is appropriate when you need significant control over the compute environment.

Examples:

```text
Custom OS configuration
Custom kernel requirements
Legacy application
Special software dependencies
Long-running application
Specific instance architecture
GPU workloads
Custom networking
Third-party software installation
Application requiring persistent server configuration
```

Example:

You have a legacy application:

```text
Java application
      ↓
Specific RHEL version
      ↓
Custom kernel module
      ↓
Custom monitoring agent
      ↓
Custom filesystem
      ↓
EC2
```

A more abstract service might restrict some of these requirements.

EC2 gives you control.

---

# 3. Is EC2 operational overhead?

Yes.

This is one of the most important exam distinctions.

EC2 is IaaS.

AWS manages the underlying infrastructure.

You still manage the server.

```text
EC2
│
├── OS patching
├── Security hardening
├── Application installation
├── Runtime
├── Monitoring
├── Scaling
├── Backup strategy
└── Configuration
```

Therefore:

```text
EC2 = Maximum control among the two
       +
    Higher operational responsibility
```

This does not mean EC2 is always the wrong answer.

SAP-C02 often gives you a requirement where the additional control is necessary.

---

# 4. Minimal requirements for EC2

You generally need:

```text
VPC
 └── Subnet
      └── EC2 instance
```

Typical production architecture:

```text
Route 53
    ↓
CloudFront / ALB
    ↓
Target Group
    ↓
Auto Scaling Group
    ↓
EC2 instances
    ↓
RDS / DynamoDB
```

For production workloads, a single EC2 instance is usually not the desired architecture if availability and scalability matter.

Think:

```text
EC2
+
Auto Scaling
+
Load Balancer
+
Multi-AZ
```

# 5. EC2 scaling

EC2 itself provides compute.

It does not automatically give you application-level scaling.

You typically associate it with:

Amazon EC2 Auto Scaling.

Example:

```text
ALB
 ↓
Auto Scaling Group
 ↓
EC2
EC2
EC2
```

When demand increases:

```text
2 instances
    ↓
5 instances
```

When demand decreases:

```text
5 instances
    ↓
2 instances
```

This is horizontal scaling.

You also have vertical scaling:

```text
t3.medium
    ↓
m7i.large
```

But vertical scaling usually requires changing the instance configuration and often restarting or replacing the instance.

For SAP-C02, when the question emphasizes elasticity, think Auto Scaling.

# 6. EC2 cost model

EC2 cost has several dimensions.

```text
Compute
+
EBS
+
Data transfer
+
Elastic IP where applicable
+
Load Balancer
+
Monitoring
+
Backup
```

The EC2 instance itself is only one part of the bill.

Common purchasing models include:

```text
On-Demand
Reserved Instances
Savings Plans
Spot Instances
Dedicated Hosts
Dedicated Instances
```

For SAP-C02, the workload pattern matters.

### On-Demand

Use when:

```text
Unpredictable workload
Short-term workload
Cannot commit
```

Higher unit cost.

### Savings Plans

Use when:

```text
Predictable compute usage
Long-term commitment
Need flexibility across compute usage
```

You commit to spend rather than a specific EC2 configuration in the same way as a traditional reservation.

### Reserved Instances

Useful when:

```text
Predictable EC2 workload
Long-term usage
Specific instance configuration
```

### Spot

Use when:

```text
Fault-tolerant
Stateless
Flexible timing
Batch processing
Distributed workloads
```

Avoid Spot for workloads requiring uninterrupted capacity unless you have designed around interruptions.

# 9. Why EC2 instead of Elastic Beanstalk?

Choose EC2 when the workload requires server-level control.

Examples:

```text
"Custom OS configuration"
"Install kernel module"
"Full control over instances"
"Legacy application requiring custom server configuration"
"Specific AMI requirements"
"Custom software installed on the host"
```

These clues push you toward EC2.

---

# 10. AWS Elastic Beanstalk

Now the important comparison.

## Why did Elastic Beanstalk exist?

Elastic Beanstalk exists because many developers don't want to manage servers.

Imagine a developer has:

```text
Java application
```

They don't want to manually handle:

```text
EC2
AMI
OS
Auto Scaling
Load Balancer
Deployment
Health checks
Capacity
```

They want:

```text
Upload application
        ↓
Beanstalk
        ↓
AWS provisions environment
        ↓
Application runs
```

Beanstalk abstracts much of the infrastructure management.

---

# 11. What problem does Elastic Beanstalk solve?

It solves:

"How do I deploy and operate a web application without manually managing the underlying AWS infrastructure?"

You provide application code.

Beanstalk manages much of the environment provisioning and application deployment.

Conceptually:

```text
Application Code
       ↓
Elastic Beanstalk
       ↓
┌───────────────────┐
│ Load Balancer     │
│ Auto Scaling      │
│ EC2               │
│ Application       │
└───────────────────┘
```

Important point:

Elastic Beanstalk does not replace EC2.

It uses AWS infrastructure such as EC2 underneath.

---

# 12. Is Elastic Beanstalk operational overhead?

Lower than EC2.

But it is not serverless.

You still have infrastructure underneath.

Think:

```text
EC2
│
│ More management
│
Elastic Beanstalk
│
│ More platform automation
│
Serverless services
```

Beanstalk handles much of:

```text
Environment provisioning
Deployment
Capacity provisioning
Auto Scaling configuration
Load balancing integration
Application health monitoring
```

You still need to understand the underlying infrastructure.

---

# 13. Minimal requirements for Elastic Beanstalk

At the application level:

```text
Application
    ↓
Supported platform/runtime
    ↓
Elastic Beanstalk environment
```

Beanstalk then provisions resources.

For example:

```text
Elastic Beanstalk
       ↓
     ALB
       ↓
Auto Scaling Group
       ↓
     EC2
```

This is why Beanstalk is classified as a managed application platform rather than serverless compute.

---

# 14. Elastic Beanstalk cost

This is a classic exam point.

Elastic Beanstalk itself has no additional service charge for the core service.

You pay for the underlying resources.

For example:

```text
Beanstalk
   ↓
EC2        → Pay for EC2
ALB        → Pay for ALB
EBS        → Pay for EBS
Data       → Pay applicable transfer charges
```

Therefore:

```text
Beanstalk does not mean "free compute."
```

It reduces operational effort rather than eliminating infrastructure costs.

# 28. Common SAP-C02 Exam Traps

### Trap 1: Beanstalk is serverless

Wrong.

Beanstalk uses infrastructure such as EC2.

```text
Beanstalk ≠ Serverless
```

---

### Trap 2: Beanstalk eliminates EC2

Wrong.

Beanstalk manages an application environment built using AWS infrastructure.

---

### Trap 3: Beanstalk is always cheaper than EC2

Wrong.

Beanstalk reduces operational work. The underlying resources still generate charges.

---

### Trap 4: EC2 is always the most flexible answer

Technically it gives more control, but SAP-C02 asks for the optimal architecture.

If the requirement says:

```text
Minimize operational overhead
+
Standard web application
+
Supported runtime
```

Beanstalk is often a better architectural choice.

---

### Trap 5: Choose EC2 because migration requires minimal changes

Not automatically.

Ask what "minimal changes" means.

If the application needs its existing OS and server configuration:

```text
EC2
```

If the application fits a supported Beanstalk platform and the goal is reduced management:

```text
Beanstalk
```
