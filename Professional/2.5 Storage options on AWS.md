### S3 Storage Classes Feature Breakdown

| Storage Class | Access Frequency | Retrieval Time SLA | Availability SLA | Cost Profile |
| :--- | :--- | :--- | :--- | :--- |
| **S3 Standard** | Frequent | Milliseconds | $99.99\%$ | Highest storage / Lowest retrieval |

> [!IMPORTANT]
> **Exam Rule 1: S3 Versioning vs. Object Lock**:
> - **Versioning**: Protects against accidental deletion/overwrite by retaining object revision history.
> - **Object Lock**: Enforces **Write-Once-Read-Many (WORM)** compliance (Governance or Compliance Mode) to make objects immutable against deletion by any user including root.

> [!TIP]
> **Exam Rule 2: S3 High-Throughput Ingestion**:
> - **Multipart Upload**: Mandatory for files $> 5\text{ GB}$; recommended for files $> 100\text{ MB}$ to enable parallel part uploads.
> - **S3 Transfer Acceleration**: Uses AWS CloudFront Edge Locations to accelerate uploads over long geographic distances.

## 4. Deep-Dive: Amazon EBS (Elastic Block Store) & Instance Store

### EBS Volume Types Comparison

| Volume Type | Technology | Max IOPS / Volume | Max Throughput | Primary Target Workloads |
| :--- | :--- | :--- | :--- | :--- |
| **gp3** | General Purpose SSD | $16,000$ IOPS | $1,000\text{ MB/s}$ | Default baseline for OS, web apps, dev/test |
| **io2 / io2 Block Express**| Provisioned IOPS SSD | **256,000 IOPS** | **4,000 MB/s** | Mission-critical DBs (Oracle, SQL Server, SAP HANA) |
| **st1** | Throughput Optimized HDD | $500$ IOPS | $500\text{ MB/s}$ | Big Data, Data Warehouses, Log processing |
| **sc1** | Cold HDD | $250$ IOPS | $250\text{ MB/s}$ | Infrequently accessed cold sequential workloads |

> [!WARNING]
> **Exam Trap: EBS Scope is Single-AZ**: An EBS volume resides strictly in **one Availability Zone**. You cannot directly attach an EBS volume to an EC2 instance in another AZ without creating an EBS Snapshot or using **EFS / FSx** shared file storage.

## 5. Shared File Systems: EFS vs. Amazon FSx Family

- **Amazon EFS**: Fully managed POSIX NFS file system for **Linux workloads**. Multi-AZ durability; accessible concurrently by thousands of EC2 instances.
- **FSx for Windows File Server**: Fully managed **SMB file system** with native Microsoft Active Directory integration, Windows ACLs, and SMB performance.
- **FSx for Lustre**: High-performance parallel file system designed for **HPC, Machine Learning training, and financial modeling**.
- **FSx for NetApp ONTAP**: Enterprise multi-protocol storage (NFS, SMB, iSCSI) with NetApp ONTAP data management features.

## 9. Common SAP-C02 Exam Traps

1. **Trap 1: Selecting EBS for Multi-EC2 Shared Access**: Standard EBS volumes cannot be shared across multiple instances in different AZs. Use **Amazon EFS** (for Linux) or **Amazon FSx** (for Windows).
2. **Trap 2: Confusing AWS DataSync with Storage Gateway**: DataSync is an online *migration and sync tool*. Storage Gateway provides *ongoing hybrid file/block access* for on-premises servers.
3. **Trap 3: Using S3 One Zone-IA for Critical Single-Copy Data**: One Zone-IA stores data in only one AZ. If that AZ experiences an outage, data is unavailable. Use One Zone-IA only for *easily reproducible data*.
4. **Trap 4: Selecting Snowball for High-Bandwidth Online Transfer**: If a high-speed Direct Connect circuit is available, use **AWS DataSync**. Use **Snowball** when network transfer would take weeks/months due to poor connectivity.
5. **Trap 5: Downloading Large Datasets from S3 on Every Boot in Auto Scaling**: Writing User Data scripts to download large static datasets (e.g., 500 GB) from S3 onto local EBS volumes on *every* new EC2 instance launch adds severe boot-time delays (15–30+ mins) and requires purchasing redundant 500 GB EBS storage per instance. Mount a single **Amazon EFS volume** instead.

## 9.1 Real-World Exam Scenario: Auto-Scaling Fleet with 500 GB Shared Dataset & SSM Patching

- **Scenario**: A company needs an auto-scaling EC2 deployment solution with the following strict requirements:
  - Must access a **500 GB static dataset** immediately upon boot.
  - Must scale out/in based on traffic spikes.
  - Development team needs to deploy code updates **several times a day**.
  - Operating system security patches must be installed **within 48 hours** of release.
  - Must be cost-effective.
- **Architecture Solution**:

### Architectural Key Points:
1. **Amazon EFS vs. S3 Download & EBS**: Mounting a single shared **Amazon EFS volume** provides instant NFS access to the 500 GB dataset upon boot. It avoids paying for 500 GB EBS volumes on every auto-scaling instance and eliminates long 500 GB download delays during scale-out events.
2. **AWS Systems Manager Automation for OS Patching**: Systems Manager installs OS security patches and bakes an updated AMI to satisfy the 48-hour patching SLA via instance replacement.
3. **AWS CodeDeploy for Frequent Code Updates**: Allows developers to push code updates to running instances multiple times a day independently of AMI baking cycles or nightly batch windows.

### Why Distractor Options Fail:
- *S3 Download via User Data + EBS per Instance*: Downloading 500 GB from S3 on every launch adds 15–30+ minutes to boot times (stalling auto-scaling during traffic spikes) and multiplies EBS storage costs across every instance in the fleet.
- *Nightly Batch Job for Code Deployments*: Batch jobs run once a night, failing the requirement to deploy code updates **several times during the day**.
- *Waiting for New AWS Amazon Linux AMI Releases*: Amazon Linux AMI releases occur over weeks/months, failing the requirement to patch security vulnerabilities within **48 hours** of release.

## 9.2 Real-World Exam Scenario: Hybrid POSIX Block Storage Scaling for 1,000 TB Dataset (Gateway-Cached Volumes [1,024 TB Limit] vs. Gateway-Stored Volumes [512 TB Limit] & S3/Glacier Traps)

### Storage Gateway Volume Types Comparison Matrix

| Storage Gateway Type | Primary Data Location | Local Cache / On-Prem Hardware | Max Volume Capacity | Protocol Interface | Key Exam Trigger |
| :--- | :--- | :--- | :---: | :--- | :--- |
| **Gateway-Cached Volumes** | **Amazon S3** (Cloud) | Frequently accessed data cached locally | **1,024 TB (1 PB)** | POSIX iSCSI Block | *"Scale storage to AWS for 1,000 TB dataset with low local cache"* |
| **Gateway-Stored Volumes** | **On-Premises SAN/NAS** | 100% full dataset stored locally | **512 TB** (Hard Limit) | POSIX iSCSI Block | *"Maintain 100% primary data locally on-premises"* |
| **S3 File Gateway** | **Amazon S3** (Objects) | Frequently accessed files cached locally | Unlimited (S3 scale) | NFS / SMB File | *"On-prem file server interface (NFS/SMB) directly to S3"* |
| **Tape Gateway (VTL)** | **Amazon S3 / Glacier** | Virtual tape catalog cached locally | Unlimited (Tape scale)| iSCSI VTL Tape | *"Replace physical on-premises tape backup infrastructure"* |

---

- **Scenario**: A shipping firm running legacy non-x86 servers on-premises needs to scale its data storage using AWS. A backup application requires **POSIX-compatible block-based storage (iSCSI)** mounted to a single folder on-premises. A total of **1,000 TB (1 PB)** of data must be mounted, and users must access portions of this data locally while backups occur. What backup solution is most appropriate?
- **Architecture Solution**:
  - Provision **Gateway-Cached Volumes** from **AWS Storage Gateway**.

```mermaid
    end

        S3Primary[("Amazon S3 Bucket<br/>📦 Primary Storage for 1,000 TB Volume<br/>(Max Capacity: 1,024 TB per volume)")]
        SGAppliance <==|"SSL/TLS Asynchronous Data Sync"==> S3Primary
    end

    classDef onprem fill:#fff3cd,stroke:#ffc107,stroke-width:1px;
    classDef cloud fill:#2b8a3e,stroke:#1e632b,color:#ffffff;

```

### Key Technical Rationale:
1. **1,024 TB Capacity Support for Gateway-Cached Volumes**: Gateway-Cached volumes store primary data in Amazon S3 and support volume sizes up to **1,024 TB (1 PB)** per volume, perfectly accommodating the 1,000 TB dataset.
2. **POSIX Block (iSCSI) Compatibility**: Storage Gateway Volume Gateways present standard iSCSI target block volumes that mount directly to legacy non-x86 servers as local POSIX-compatible block devices.

### Why Distractor Options Fail:
- *Provision Gateway-Stored Volumes from AWS Storage Gateway (Your Selection)*:
  - **Gateway-Stored Volumes have a hard capacity limit of 512 TB per volume**! Mounting a 1,000 TB dataset in a single volume fails on Gateway-Stored volumes. Furthermore, Gateway-Stored volumes require purchasing 1,000 TB of expensive physical local SAN hardware.
- *Use Amazon S3 directly as backup target*:
  - Amazon S3 is object storage accessed via REST APIs (HTTP GET/PUT); it is **NOT** POSIX-compatible block storage (iSCSI) that can be mounted as a local block device folder to legacy non-x86 servers.
- *Use Amazon Glacier directly as backup target*:
  - Amazon Glacier is an offline archival vault with 3 to 5 hour retrieval delays; it cannot serve live POSIX block reads to active users during backup jobs.

## 9.3 Real-World Exam Scenario 3: Multi-AZ Windows Server CMS Shared Storage (FSx for Windows File Server vs. EFS, FSx for Lustre & EBS Multi-Attach Traps)

- **Scenario**: A media company deploys a Windows-based Content Management System (CMS) application across a 3-Availability Zone Amazon EC2 Auto Scaling group. All instances must access the exact same shared data files simultaneously across AZs. The storage solution must support **Windows ACLs (NTFS permissions)**, natively integrate with **Microsoft Active Directory**, and require minimal management overhead. What is the recommended storage solution?
- **Architecture Solution**:
  - Deploy a new Windows AMI for an Auto Scaling group spanning 3 Availability Zones (AZs).
  - Create an **Amazon FSx for Windows File Server** file system for shared storage.
  - Write a UserData script to install the CMS application, mount the FSx for Windows File Server SMB share, and join the instances to the Active Directory domain.

### Key Technical Rationale:
1. **Amazon FSx for Windows File Server for Windows ACLs & SMB**:
   - Amazon FSx for Windows File Server is built on Microsoft Windows Server, providing native SMB protocol file shares with full support for **Windows ACLs (NTFS file permissions)**, Microsoft Active Directory domain integration, shadow copies, and data deduplication.
   - It supports Multi-AZ deployment configurations, providing seamless shared file access across EC2 instances running in different Availability Zones.

### Why Distractor Options Fail:
- *Amazon Elastic File System (Amazon EFS)*:
  - **Linux NFS Only, No Windows ACLs**: Amazon EFS uses the NFSv4 protocol designed for Linux operating systems; it does NOT natively support Windows ACLs (NTFS permissions) or SMB protocol required by Windows Server EC2 instances.
- *Amazon FSx for Lustre*:
  - **Linux HPC POSIX File System**: Amazon FSx for Lustre is a high-performance POSIX file system designed for Linux HPC, AI/ML, and fast S3 processing; it does NOT run on Windows Server or support Windows ACLs/Active Directory.
- *Amazon EBS Multi-Attach*:
  - **Single-AZ Limitation**: EBS Multi-Attach allows attaching a Provisioned IOPS (io1/io2) volume to multiple instances in the **SAME Availability Zone ONLY**! It cannot span across multiple AZs. Furthermore, it requires a cluster-aware file system (like GFS2/OCFS2), not standard Windows NTFS/ReFS.
