## 5. Calculate Transfer Time Before Choosing Between DataSync and Snowball

> [!TIP]
> **Data Volume ÷ Effective Bandwidth Formula**:
> Do not assume large data automatically means Snowball. Calculate the transfer duration:
> $$\text{Transfer Time} = \frac{\text{Total Data Volume (Bits)}}{\text{Available Network Bandwidth (Bps)}}$$
> - **100 TB over a 10 Gbps Direct Connect**: $\approx 24$ hours $\rightarrow$ Select **AWS DataSync**.
> - **100 TB over a 100 Mbps VPN Link**: $\approx 100+$ days $\rightarrow$ Select **AWS Snowball Edge**.

## 10.5 Real-World Exam Scenario: Hybrid Media Archival Tagging (S3 File Gateway + Rekognition vs. Kinesis Video Streams Trap)

- **Scenario**: A major entertainment studio maintains a 50+ TB video archive on-premises managed by a Media Asset Management (MAM) system. The studio wants an automated tagging system using facial recognition (Amazon Rekognition) to catalog actors across the archive while gradually migrating assets to AWS with **minimal disruption** and **least operational overhead**. What is the optimal solution?
- **Architecture Solution**:
  - Set up an on-premises **AWS Storage Gateway (S3 File Gateway)** appliance. Configure the MAM solution to write video files to the File Gateway file share (which asynchronously backs files into Amazon S3). Use an **AWS Lambda function** triggered by S3 uploads to invoke the **Amazon Rekognition** SDK to build a face collection (`IndexFaces`/`StartFaceSearch`) and persist facial metadata back into the MAM solution.

### Why Distractor Options Fail:
- *Amazon Kinesis Video Streams (Your Selection)*:
  - Kinesis Video Streams is designed for real-time live camera feed ingestion (RTSP/WebRTC from IoT/security cameras), NOT for processing existing 50+ TB archival video files! Refactoring an existing MAM system to stream pre-recorded 50 TB archival files into Kinesis Video Streams requires massive custom code refactoring, high operational complexity, and stream consumer management.
- *Tape Gateway + Real-time Rekognition from Tape*:
  - Tape Gateway archives virtual tapes directly into Amazon S3 Glacier / S3 Glacier Deep Archive. Amazon Rekognition **CANNOT directly process objects stored in S3 Glacier in real-time** without an expensive, multi-hour retrieval process! Tape Gateway is strictly for cold tape backup, not live file access for ML APIs.
- *AWS DataSync + EC2 Instance running OpenFace/OpenCV*:
  - Installing open-source facial recognition software on self-managed EC2 instances introduces massive operational management overhead (OS patching, scaling, custom ML model tuning) compared to using fully managed Amazon Rekognition + AWS Lambda.

## 10.6 Real-World Exam Scenario: Securing AWS Storage Gateway iSCSI Volume Gateway against Replay Attacks (CHAP Authentication)

- **Scenario**: A commercial bank uses **AWS Storage Gateway (Volume Gateway)** to present block storage to on-premises servers via **iSCSI**. The security team detects network replay attacks and IP packet substitution masquerade attempts trying to intercept and re-transmit iSCSI data. How can the Solutions Architect secure the Storage Gateway against these attacks?
- **Architecture Solution**:
  - Configure **Challenge-Handshake Authentication Protocol (CHAP)** to authenticate iSCSI target and initiator connections on the Volume Gateway.

```mermaid
flowchart TD
    subgraph OnPremHost["1. On-Premises Application Server"]
        Initiator["iSCSI Initiator<br/>(Host Server requesting block storage)"]
    end

    subgraph SecurityProtocol["2. Challenge-Handshake Authentication Protocol (CHAP)"]
        Challenge["1. Storage Gateway sends random Challenge string"]
        Response["2. Initiator computes Hash using Shared Secret & responds"]
        Verify["3. Gateway verifies response before granting block access"]

        Initiator ==> Challenge ==> Response ==> Verify
    end

    subgraph StorageGatewayTier["3. AWS Storage Gateway Tier"]
        VolumeGateway["AWS Storage Gateway (Volume Gateway)<br/>🔒 iSCSI Target Protected by CHAP"]
        S3Storage[("Amazon S3 Bucket<br/>(Encrypted Volume Storage)")]

        Verify ==> VolumeGateway ==> S3Storage
    end

    classDef host fill:#d1ecf1,stroke:#17a2b8,stroke-width:1px;
    classDef chap fill:#7950f2,stroke:#5f3dc4,color:#ffffff;
    classDef gw fill:#2b8a3e,stroke:#1e632b,color:#ffffff;

    class Initiator host;
    class Challenge,Response,Verify chap;
    class VolumeGateway,S3Storage gw;
```

### Key Technical Rationale:
1. **iSCSI Security via CHAP Authentication**: **Challenge-Handshake Authentication Protocol (CHAP)** provides mutual authentication between iSCSI initiators (on-premises servers) and iSCSI targets (AWS Storage Gateway). CHAP prevents playback/replay attacks by requiring dynamic challenge-response validation using a secret key before granting access to volume targets.
2. **Volume Gateway Interface Matching**: Volume Gateways (Stored and Cached Volumes) present block storage to hosts over the **iSCSI** protocol.
3. **Protocol Authentication Scope**:
   - **iSCSI (Volume Gateway / Tape Gateway)** $\longrightarrow$ Authenticated via **CHAP**.
   - **NFS (S3 File Gateway)** $\longrightarrow$ Controlled via Client IP export rules & AWS IAM roles.
   - **SMB (S3 / FSx File Gateway)** $\longrightarrow$ Authenticated via Active Directory (NTLM / Kerberos).

### Why Distractor Options Fail:
- *Configure CHAP for NFS connections*:
  - CHAP is strictly an **iSCSI block authentication protocol**. NFS (Network File System) does NOT support CHAP authentication.
- *Replace iSCSI with CIFS/SMB*:
  - Replacing iSCSI with CIFS/SMB converts block storage into file storage, breaking raw block database volume requirements, and does not directly provide iSCSI replay protection.
- *Replace iSCSI Block Interface with iSCSI Virtual Tape Library (VTL)*:
  - The iSCSI VTL interface is specifically designed for **Tape Gateways** used by backup software (Veeam, Commvault), NOT for application block volume storage on Volume Gateways.

## 10.7 Real-World Exam Scenario 7: Global Long-Distance S3 Upload Acceleration (S3 Transfer Acceleration vs. CloudFront Custom Origin & Global Accelerator Traps)

- **Scenario**: A web application allows artists in North America and Europe to upload large, high-resolution artwork photos directly to a centralized Amazon S3 bucket located in `us-east-1`. European artists report slow upload performance when uploading images across the Atlantic over the public internet. What is the **BEST solution** to improve image upload performance?
- **Architecture Solution**:
  - Enable **Amazon S3 Transfer Acceleration** on the central S3 bucket.
  - Update the client application upload endpoint to use the **`s3-accelerate` endpoint domain** (`bucketname.s3-accelerate.amazonaws.com`).

```mermaid

    end

    subgraph EdgeTier ["2. Globally Distributed Edge Ingestion Tier"]
        EdgeLocation["Amazon CloudFront Edge Location (Europe)<br/>⚡ Low-Latency Public Internet Ingestion"]
        EU_Artists ==>|"1. Rapid Local ISP Upload"| EdgeLocation
    end

    subgraph AWSBackbone ["3. Optimized Private AWS Global Backbone"]
        Backbone["AWS Global Private Network Backbone<br/>🚀 Congestion-Free Optimized Network Routing"]
        EdgeLocation ==>|"2. Private Backbone Transit"| Backbone
    end

    subgraph TargetStorage ["4. Centralized Storage Destination (us-east-1)"]
        S3Bucket[("Amazon S3 Central Bucket<br/>(Region: us-east-1)")]
        Backbone ==>|"3. Accelerated S3 PutObject"| S3Bucket
    end

    classDef client fill:#fff3cd,stroke:#ffc107,stroke-width:1px;
    classDef edge fill:#7950f2,stroke:#5f3dc4,color:#ffffff;
    classDef backbone fill:#1864ab,stroke:#0b5394,color:#ffffff;

    class EdgeLocation edge;
    class Backbone backbone;
    class S3Bucket storage;
```

### Key Technical Rationale:
1. **Amazon S3 Transfer Acceleration Mechanics**:
   - S3 Transfer Acceleration takes advantage of Amazon CloudFront's globally distributed Edge Locations.
   - When data arrives at a local European edge location, it is immediately routed to the `us-east-1` S3 bucket over the optimized, congestion-free **AWS private global network backbone**, bypassing public internet BGP routing delays.
2. **Dedicated Acceleration Endpoint**: Enrolling a bucket enables the `s3-accelerate.amazonaws.com` DNS endpoint, requiring zero complex application code changes beyond updating the endpoint URL.

### Why Distractor Options Fail:
- *CloudFront Distribution as Custom Origin for S3 Uploads*:
  - While CloudFront supports HTTP PUT/POST methods, CloudFront origins have a strict **60-second connection timeout** limit! Uploading large multi-gigabyte artwork files over CloudFront takes several minutes, causing connection timeouts and upload failures. S3 Transfer Acceleration is specifically designed for long-distance S3 object uploads without origin timeouts.
- *Multipart Upload Alone over Public Internet*:
  - Multipart upload allows parallel uploading of file parts, but if the network route across the Atlantic is congested over public internet BGP routing, multipart upload still suffers high packet loss and latency.
- *AWS Global Accelerator in Front of EC2 Instances*:
  - Global Accelerator accelerates network traffic to EC2/ALB endpoints; however, artwork photos are uploaded directly from mobile clients to the S3 bucket, NOT through EC2 instances! Adding Global Accelerator in front of EC2 instances does not accelerate direct S3 bucket `PUT` requests.

## 11. Common SAP-C02 Exam Traps

1. **Trap 1: Selecting Snowball Purely Based on Terabyte Size**: If a company has a 10 Gbps Direct Connect connection, 100 TB can migrate via DataSync in one day. Always calculate transfer time based on bandwidth before picking physical appliances.
2. **Trap 2: Using AWS Transfer Family for Bulk Server Storage Migration**: Transfer Family provides an SFTP client endpoint. For automated bulk file server migration, choose **AWS DataSync**.
3. **Trap 3: Confusing CloudFront with S3 Transfer Acceleration**: CloudFront caches content for global browser downloads. For accelerating client uploads directly to S3, select **S3 Transfer Acceleration**.
4. **Trap 4: Using Storage Gateway for One-Time File Migration**: Storage Gateway creates a persistent hybrid caching layer. For one-time or scheduled data migration, choose **AWS DataSync**.
5. **Trap 5: Confusing iSCSI CHAP Authentication with NFS/SMB Security**: CHAP (Challenge-Handshake Authentication Protocol) is strictly an **iSCSI block-level authentication protocol** used to secure **AWS Storage Gateway Volume Gateways** against network replay attacks. NFS uses IP export rules/IAM; SMB uses Active Directory.
6. **Trap 6: Using CloudFront Custom Origin for Large Long-Distance S3 Uploads**: CloudFront custom origins enforce a strict 60-second connection timeout that breaks large multi-minute file uploads. To accelerate long-distance global uploads directly to S3 without timeouts, always select **Amazon S3 Transfer Acceleration** (`s3-accelerate`).
