# AWS — Using Service Endpoints for Service Integrations

For the AWS exam, this topic is mainly about answering:

> **"How does my workload access an AWS service, and should that traffic go through the public Internet, a NAT Gateway, an Internet Gateway, or a private endpoint?"**

The most important services/concepts are:

* **VPC endpoints**
* **Gateway endpoints**
* **Interface endpoints / AWS PrivateLink**
* **AWS service endpoints**
* **Endpoint policies**
* **Private DNS**
* **Route 53 Resolver**
* **NAT Gateway**
* **Internet Gateway**
* **Transit Gateway**
* **Cross-account PrivateLink**

---

# 1. Start With the Big Picture

Suppose an EC2 instance in a private subnet needs to access S3.

You have two broad approaches:

### Without VPC endpoint

```mermaid
flowchart LR
    EC2["EC2 (Private Subnet)"] --> NAT["NAT Gateway"] --> IGW["Internet Gateway"] --> S3Public["AWS S3 Public Endpoint"]
```

### With VPC endpoint

```mermaid
flowchart LR
    EC2Priv["EC2 (Private Subnet)"] --> VPCE["VPC Endpoint"] --> S3Direct["Amazon S3"]
```

The second architecture can avoid sending the service traffic through a NAT Gateway.

---

# 2. What Is a VPC Endpoint?

A **VPC endpoint** provides private connectivity from a VPC to supported AWS services and endpoint services without requiring an Internet Gateway for that service traffic.

Think:

```mermaid
flowchart LR
    VPC["Amazon VPC"] -->|"Private Connectivity"| VPCE["VPC Endpoint"] --> AWSService["AWS Service"]
```

Examples:

```text
EC2 → S3
EC2 → DynamoDB
EC2 → Secrets Manager
EC2 → SSM
EC2 → ECR
EC2 → CloudWatch
```

The exact endpoint type depends on the service.

---

# 3. Why Use VPC Endpoints?

The exam usually gives you one or more of these requirements:

* Keep traffic private
* Avoid Internet/NAT Gateway
* Reduce NAT Gateway costs
* Reduce operational overhead
* Improve security posture
* Restrict access to specific AWS services
* Allow private-subnet workloads to access AWS services

Then think:

> **VPC Endpoint**

---

```mermaid
flowchart TD
```

# 5. Gateway Endpoint

Gateway endpoints are used for:

* **Amazon S3**
* **Amazon DynamoDB**

That's the exam shortcut.

```mermaid
flowchart LR
    PrivSub["Private Subnet"] --> RT["Route Table"] --> GWEP["Gateway Endpoint"] --> Target["S3 / DynamoDB"]
```

No NAT Gateway is required for this service traffic.

---

# 6. Gateway Endpoint HLD

Example:

```mermaid
flowchart TD
    subgraph VPC["Amazon VPC"]
        subgraph SubnetA["Private Subnet A"]
            EC2A["EC2 Instance"]
        end
        subgraph SubnetB["Private Subnet B"]
            EC2B["EC2 Instance"]
        end

        EC2A --> RT["VPC Route Table"]
        EC2B --> RT
        RT --> GWEP["S3 Gateway Endpoint"]
    end

    GWEP --> S3["Amazon S3"]
```

The endpoint is associated with route tables.

---

# 7. Gateway Endpoint — Why It's Attractive

### Cost

Gateway endpoints for S3/DynamoDB have **no additional endpoint hourly charge**.

That's a very useful exam clue.

Compare:

```mermaid
flowchart LR
    NAT["NAT Gateway"] --> Cost1["Hourly + Data Processing Charges"]
```

versus:

```mermaid
flowchart LR
    GWEP["S3 Gateway Endpoint"] --> Cost2["No Additional Endpoint Hourly Charge"]
```

Therefore:

> **Private EC2 → S3/DynamoDB with minimum cost → Gateway Endpoint**

---

# 8. Interface Endpoint

Interface endpoints use **AWS PrivateLink**.

Think:

```mermaid
flowchart LR
    PrivSub["Private Subnet"] --> ENI["Endpoint ENI (Interface Endpoint)"] --> Service["AWS Service"]
```

Unlike a Gateway Endpoint, an interface endpoint creates **elastic network interfaces (ENIs)** in your subnets.

---

Common exam examples:

```mermaid
flowchart TD

        subgraph SubnetA["Private Subnet A"]
            EC2A["EC2 Instance A"] --> ENIA["Interface Endpoint ENI-A"]
```

# 11. Gateway vs Interface Endpoint

Memorize this table:

| Feature | Gateway Endpoint | Interface Endpoint |
|---|---|---|
| Technology | VPC endpoint | AWS PrivateLink |
| Main examples | S3, DynamoDB | Many AWS services |
| Uses ENI | ❌ | ✅ |
| Route table based | ✅ | Uses ENI/IP routing |
| Private IP | Not in same ENI model | ✅ |
| Hourly endpoint charge | No additional charge | ✅ Typically |
| Data processing charge | No endpoint charge | Applicable |
| Security Group | Not attached like interface ENI | ✅ |
| Private DNS | Not the same mechanism | Commonly used |
| Exam keyword | S3/DynamoDB | PrivateLink |

# 14. NAT Gateway vs VPC Endpoint

This is a **high-value exam comparison**.

| Requirement | NAT Gateway | VPC Endpoint |
|---|---|---|
| Private subnet → Internet | ✅ | ❌ |
| Private subnet → supported AWS service | Possible | ✅ Preferred |
| Private connectivity to AWS service | ❌ | ✅ |
| General Internet access | ✅ | ❌ |
| Avoid NAT charges for service traffic | ❌ | ✅ |
| Central service-specific access | ❌ | ✅ |
| Operational overhead | Medium | Low/Medium |

### Key rule:

> **Don't use a NAT Gateway just because an EC2 instance is in a private subnet. First ask whether the destination is an AWS service that can be reached through a VPC endpoint.**

# 18. Endpoint Policies

VPC endpoints can also help control what access is allowed.

For example:

```mermaid
flowchart LR
    EC2["EC2"] --> GWEP["S3 Gateway Endpoint"] --> Policy{"Endpoint Policy"}
    Policy -->|Allowed| BucketA["Bucket-A ✅"]
    Policy -. "Blocked" .- BucketB["Bucket-B ❌"]
```

This provides another layer of control.

But remember:

> **Endpoint policy does not replace IAM policies or bucket policies.**

Think of authorization as potentially involving multiple policy layers.

---

# 19. Security Groups with Interface Endpoints

Interface endpoints use ENIs.

Therefore, security groups can control access to those endpoint ENIs.

Example:

```mermaid
flowchart LR
    EC2["EC2 (EC2 SG)"] -->|TCP 443| ENI["Endpoint ENI (Endpoint SG)"] --> Service["AWS Service"]
```

If the endpoint's security group doesn't allow the traffic:

```mermaid
flowchart LR
    EC2["EC2"] -. "❌ Blocked by Endpoint SG" .- ENI["Endpoint ENI"]
```

Traffic fails.

# 20. Private DNS

This is another important concept.

Suppose your application calls:

```text
secretsmanager.<region>.amazonaws.com
```

With private DNS enabled for the interface endpoint, DNS can resolve the service hostname to the endpoint's private IP addresses.

Conceptually:

```mermaid
flowchart LR
    App["Application"] -->|"1. Query Hostname"| R53["Route 53 Resolver"] -->|"2. Return Private IP"| ENI["Interface Endpoint Private IP"] -->|"3. Connect Privately"| Service["AWS Service"]
```

The application can continue using the normal AWS service hostname.

---

# 21. Without Private DNS

You may need to explicitly use endpoint-specific DNS names depending on the architecture.

This creates more application/configuration complexity.

Therefore:

> **Private DNS often reduces application changes and operational overhead.**

# 22. Route 53 Resolver's Role


So:

> **VPC endpoint + private DNS + Route 53 Resolver**

is a common private service-access pattern.

# 23. Endpoint Services — Not Just AWS Services

PrivateLink can also be used for **private access to services provided by other organizations/accounts**.

Architecture:

```mermaid
flowchart LR
    Consumer["Consumer VPC"] --> IFEP["Interface Endpoint"] --> PL["AWS PrivateLink"] --> Service["Endpoint Service"] --> Provider["Provider VPC"]
```

This is powerful.

You can expose:

> **a specific service rather than the entire VPC.**

# 24. PrivateLink vs VPC Peering

Very important.

### VPC Peering

```mermaid
flowchart LR
    VPCA["VPC-A"] <== "Network-Level Connectivity" ==> VPCB["VPC-B"]
```

Provides network-level connectivity.

### PrivateLink

```mermaid
flowchart LR
    Consumer["Consumer VPC"] -->|"Service-Level Connectivity"| Service["Specific Service API"]
```

Provides **service-level connectivity**.

# 25. Exam Clue: "Access Only One Service"

Question:

> "VPC-A needs access to an application hosted in VPC-B, but should not have general network access to VPC-B."

Think:

**AWS PrivateLink**

Architecture:

```mermaid
flowchart LR
    VPCA["VPC-A"] --> IFEP["Interface Endpoint"] --> PL["PrivateLink"] --> Service["Target Service"] --> VPCB["VPC-B"]
```

Not VPC Peering.

---

# 26. PrivateLink — Least Operational Overhead

Compare:

### VPC Peering

```text
VPC-A ←→ VPC-B
```

You need to manage:

* Routes
* CIDRs
* Security controls
* Connectivity relationships

### PrivateLink

```text
Consumer → Service
```

The consumer gets access to the specific service.

This reduces network exposure.

# 29. But Don't Create Endpoints for Everything

This is an important **cost/overengineering** point.

Interface endpoints generally have:

* Hourly charges per endpoint/ENI
* Data processing charges

So don't blindly create dozens of endpoints if the requirements don't justify them.

You need to balance:

```text
NAT Gateway cost
       vs
Interface Endpoint cost
       vs
Security requirement
       vs
Operational simplicity
```

## 🔒 Troubleshooting AWS Fargate Container Pull Errors (`CannotPullContainerError`)

When deploying AWS Fargate tasks in a **private subnet**, a common container launch error occurs when the Fargate task ENI cannot reach Amazon ECR to pull image layers:

```text
CannotPullContainerError: API error (500): Get https://111122223333.dkr.ecr.us-east-1.amazonaws.com/v2/: net/http: request canceled while waiting for connection
```

```mermaid
flowchart TD
    subgraph ProblemState["Problem: Fargate Task Isolated in Private Subnet"]
        FargateTask1["Fargate Task ENI<br/>(Auto-Assign Public IP: DISABLED)"] -- "x Connection Timeout (500 API Error)" --> ECR1["Amazon ECR Endpoint<br/>(dkr.ecr.us-east-1.amazonaws.com)"]
        PrivateSubnet1["Private Subnet<br/>(No NAT Gateway & No VPC Interface Endpoint)"]
    end

    subgraph SolutionOptionA["Solution Option 1: NAT Gateway in PUBLIC Subnet"]
        FargateTaskA["Fargate Task ENI<br/>(Auto-Assign Public IP: DISABLED)"] ==>|"1. Route 0.0.0.0/0 to NAT"| NATGW["NAT Gateway<br/>(Must be in a PUBLIC Subnet with EIP)"]
        NATGW ==>|"2. Internet Gateway (IGW)"| ECR_Public["Amazon ECR Public Endpoint"]
    end

    subgraph SolutionOptionB["Solution Option 2: VPC Endpoints (PrivateLink)"]
        FargateTaskB["Fargate Task ENI<br/>(Auto-Assign Public IP: DISABLED)"] ==>|"1. PrivateLink Call"| ECR_VPCE["VPC Interface Endpoints<br/>• ecr.dkr & ecr.api"]
        FargateTaskB ==>|"2. Fetch Image Blobs"| S3_GWEP["S3 Gateway Endpoint<br/>(ECR stores image layers in S3)"]
    end

    style SolutionOptionA fill:#d4edda,stroke:#28a745,stroke-width:2px;
    style SolutionOptionB fill:#d1ecf1,stroke:#17a2b8,stroke-width:2px;
    style ProblemState fill:#f8d7da,stroke:#dc3545,stroke-width:1px;
```

### Valid Architectural Remedies:
1. **Option A (NAT Gateway in Public Subnet)**:
   - Task Definition: Set Auto-Assign Public IP to **`DISABLED`**.
   - Infrastructure: Deploy a **NAT Gateway in a PUBLIC Subnet** (associated with an Elastic IP and a route to an Internet Gateway `0.0.0.0/0 -> igw-xxx`).
   - Routing: Update the private subnet route table to direct outbound internet traffic to the NAT Gateway (`0.0.0.0/0 -> nat-xxx`).
2. **Option B (VPC Interface Endpoints for ECR)**:
   - Create **VPC Interface Endpoints** for `com.amazonaws.[region].ecr.dkr` and `com.amazonaws.[region].ecr.api`.
   - Create a **Gateway VPC Endpoint** for `com.amazonaws.[region].s3` (because ECR stores image layers in S3 buckets).

## 🔒 Real-World Exam Scenario: Fixing Fargate `CannotPullContainerError` in Private Subnet

- **Scenario**: A company migrates Docker workloads to AWS Fargate. The Fargate cluster is placed on a private subnet in a VPC with no direct connection outside the VPC. Launching the task fails with `CannotPullContainerError: API error (500): Get https://111122223333.dkr.ecr.us-east-1.amazonaws.com/v2/: net/http: request canceled while waiting for connection`. Which fix works?
- **Architecture Solution**:
  1. Set the Fargate task definition auto-assign public IP option to **`DISABLED`**.
  2. Launch a **NAT Gateway in the PUBLIC Subnet** of the VPC.
  3. Update the route table of the private subnet to route requests (`0.0.0.0/0`) to the NAT Gateway.

### Why Distractor Options Fail:
- *Placing NAT Gateway in the Private Subnet*: A NAT Gateway **MUST be located in a PUBLIC Subnet** with an Elastic IP and a route to an Internet Gateway. Placing a NAT Gateway in a private subnet leaves it unable to reach the internet.
- *Enabling Auto-Assign Public IP for Private Subnet Tasks + Gateway VPC Endpoint for ECR*:
  - Assigning a public IP in a private subnet does not grant internet access because private subnets lack a route to an IGW.
  - **Amazon ECR requires Interface Endpoints (PrivateLink), NOT Gateway VPC Endpoints** (Gateway endpoints exist ONLY for S3 and DynamoDB).
- *Changing Network Mode to `bridge`*: **AWS Fargate ONLY supports `awsvpc` network mode**. Fargate does NOT support `bridge`, `host`, or `none` network modes.

### Trap 7 — Placing NAT Gateway in a Private Subnet
❌ A NAT Gateway placed in a private subnet cannot reach the Internet Gateway (`igw`). A NAT Gateway **must always reside in a PUBLIC subnet**.

### Trap 8 — Expecting Gateway VPC Endpoints for ECR
❌ Gateway VPC Endpoints exist **ONLY for Amazon S3 and Amazon DynamoDB**. All other AWS services (including ECR, Secrets Manager, Systems Manager, KMS) use **Interface VPC Endpoints (AWS PrivateLink)**.

### Trap 9 — Assuming Fargate Supports Docker `bridge` Mode
❌ AWS Fargate **only supports `awsvpc` network mode**. Every Fargate task gets its own dedicated ENI.

## 12.1 Real-World Exam Scenario: AWS PrivateLink + NLB Endpoint Service Connectivity Troubleshooting (Security Groups & Subnet NACLs — Select TWO)

- **Scenario**: A central logging service runs on an Auto Scaling group of EC2 instances behind a Network Load Balancer (NLB) in a provider VPC. Client AWS accounts send log data through **AWS PrivateLink** (interface VPC endpoints). Upon testing, clients cannot submit logs to the service. Which TWO solutions will resolve the connectivity issue?
- **Architecture Solutions (Select TWO)**:
  1. **Security Group Configuration**: Ensure the security group attached to the EC2 instances hosting the logging service allows inbound traffic from the **NLB's security group** (or NLB subnet node IPs). Ensure the security group attached to the NLB allows inbound traffic from the **interface endpoint subnet**.
  2. **Subnet NACL Configuration**: Ensure the NACL associated with the **logging service subnet** allows communication to and from the **NLB subnets**. Ensure the NACL associated with the **NLB subnets** allows communication to and from the **EC2 instance subnets** running the logging service.


### Key Technical Rationale:
1. **Network Load Balancer (NLB) Security Group Rules**:
   - In a PrivateLink + NLB service architecture, traffic enters through the **Interface Endpoint ENI**, passes into **NLB Nodes**, and is forwarded to **Target EC2 Instances**.
   - The NLB security group must allow inbound traffic from the **interface endpoint subnet CIDR**.
   - The target EC2 instances receive requests from the NLB nodes. Therefore, the target EC2 security group must allow inbound traffic from the **NLB's security group** (or NLB private node IPs), NOT raw client IP blocks!
2. **Subnet-to-Subnet Network ACL (NACL) Boundaries**:
   - NACLs operate strictly at subnet boundaries.
   - Traffic flows in two hops: **Interface Endpoint Subnet $\rightarrow$ NLB Subnet $\rightarrow$ EC2 Target Subnet**.
   - The NACL on the EC2 logging target subnet must allow inbound/outbound traffic to and from the **NLB subnets** (where load balancer nodes reside), NOT direct rules to the interface endpoint subnet.

### Why Distractor Options Fail:
- *Allowing Inbound Traffic on Target EC2 SGs directly from Client IP Blocks (Your Selection)*:
  - In an NLB target architecture, target EC2 instances receive traffic from the NLB nodes / NLB security group. Raw client IP blocks are not exposed to target security groups, so allowing client IP blocks fails to authorize NLB node traffic.
- *Configuring Direct NACLs between Logging Subnets and Interface Endpoint Subnets (Your Selection)*:
  - NACLs inspect traffic passing between adjacent subnet boundaries. Because traffic passes through the **NLB subnets first**, target EC2 subnets must configure NACL rules permitting traffic to and from the **NLB subnets**, NOT the interface endpoint subnets directly.
- *Updating AMI Launch Templates or EC2 Instance Types*:
  - Updating AMIs or instance types does not resolve network layer authorization drops caused by Security Group or NACL misconfigurations.

### Trap 7 — Placing NAT Gateway in a Private Subnet
❌ A NAT Gateway placed in a private subnet cannot reach the Internet Gateway (`igw`). A NAT Gateway **must always reside in a PUBLIC subnet**.

### Trap 8 — Expecting Gateway VPC Endpoints for ECR
❌ Gateway VPC Endpoints exist **ONLY for Amazon S3 and Amazon DynamoDB**. All other AWS services (including ECR, Secrets Manager, Systems Manager, KMS) use **Interface VPC Endpoints (AWS PrivateLink)**.

### Trap 9 — Assuming Fargate Supports Docker `bridge` Mode
❌ AWS Fargate **only supports `awsvpc` network mode**. Every Fargate task gets its own dedicated ENI.

### Trap 10 — Authorizing Client IPs directly on NLB Target EC2 Security Groups or Skipping NLB Subnet NACLs
❌ In a PrivateLink + NLB architecture, target EC2 instances receive traffic from the **NLB nodes / NLB Security Group**, NOT directly from client IP blocks. Allowing raw client IP blocks in target EC2 security groups fails! Target EC2 security groups must allow inbound traffic from the **NLB's security group** (or NLB IPs), and the NLB security group must allow inbound traffic from the **interface endpoint subnet**. Furthermore, NACLs on EC2 target subnets must permit traffic to/from the **NLB subnets**, NOT the interface endpoint subnets directly!
