
Task 2.6: Determine a cost optimization strategy to meet solution goals and objectives

Skills in:

1. Identifying opportunities to select and rightsize infrastructure for cost-effective resources
    
2. Identifying appropriate pricing models
    
3. Performing data transfer modeling and selecting services to reduce data transfer costs
    
4. Developing a strategy and implementing controls for expenditure and usage awareness
    
5. IDENTIFYING AND RIGHTSIZING INFRASTRUCTURE
    

Core idea

AWS cost optimization starts with one question:

“Am I paying for resources I actually need?”

A common SAP-C02 pattern is:

Overprovisioned resource → Right-size → Lower cost

Why this exists

Applications often start with conservative infrastructure sizing.

Example:

Application needs:  
4 vCPU  
16 GB RAM

But EC2 runs with:  
16 vCPU  
64 GB RAM

You pay for 4x the compute capacity without getting equivalent value.

Problem it solves

• Overprovisioning  
• Idle resources  
• Low CPU utilization  
• Excess memory  
• Oversized databases  
• Unused EBS volumes  
• Unused Elastic IPs  
• Excessive NAT Gateway usage  
• Excessive data transfer

AWS services related

• AWS Compute Optimizer  
• AWS Cost Explorer  
• AWS Trusted Advisor  
• CloudWatch  
• AWS Auto Scaling  
• EC2  
• RDS  
• EBS  
• S3  
• Lambda

Most important exam relationship

CloudWatch  
→ Measures utilization

Compute Optimizer  
→ Recommends right-sizing

Cost Explorer  
→ Shows spending patterns

Trusted Advisor  
→ Identifies cost optimization opportunities

Auto Scaling  
→ Dynamically adjusts capacity

Example

EC2 CPU utilization:

Average = 8%

Peak = 15%

Instance is oversized.

Possible solution:

Move from m7i.2xlarge → m7i.large

But do not blindly downsize.

Check:

CPU  
Memory  
Network  
Disk I/O  
Application latency  
Peak traffic  
Scaling behavior

SAP exam thinking

Low utilization does not automatically mean “terminate”.

Ask:

Is workload variable?

If yes:  
→ Auto Scaling

Is workload predictable?

→ Reserved Instances or Savings Plans

Is workload interruptible?

→ Spot Instances

Is workload consistently oversized?

→ Right-size

Operational overhead

Low.

Compute Optimizer and Cost Explorer reduce manual analysis.

Auto Scaling introduces configuration overhead but reduces ongoing manual capacity management.

Cost

Right-sizing directly reduces compute cost.

Auto Scaling reduces the need to maintain capacity for peak traffic 24/7.

Example:

Normal traffic = 10 instances

Peak traffic = 100 instances

Bad architecture:

100 instances running continuously.

Better:

10 → 100 through Auto Scaling.

This is one of the strongest cost optimization patterns in SAP.

2. IDENTIFYING APPROPRIATE PRICING MODELS
    

This is one of the most important SAP-C02 cost areas.

Think about workload predictability first.

Use this decision model:

Unpredictable / short-term  
→ On-Demand

Predictable long-term compute  
→ Savings Plans / Reserved Instances

Interruptible workload  
→ Spot

Dedicated hardware requirement  
→ Dedicated Hosts / Dedicated Instances

Large long-term database workload  
→ Reserved DB Instances

Serverless variable workload  
→ Pay per invocation / usage

A. On-Demand

Why it exists

Provides maximum flexibility.

No long-term commitment.

Problem solved

You do not know how long the workload will exist.

Examples:

• New application  
• Development environment  
• Temporary migration  
• Short-term workload  
• Unpredictable workload

Cost

Highest baseline price.

Trade-off

Higher cost in exchange for flexibility.

Exam keyword

“Unpredictable”  
“Short-term”  
“No commitment”  
“Temporary”

B. Reserved Instances

Why it exists

Discount for committing to a specific usage pattern.

Good for predictable workloads.

Examples:

RDS database running 24/7.

EC2 workload running continuously.

Trade-off

Less flexibility than On-Demand.

Exam keyword

“Steady state”  
“24/7”  
“Predictable”  
“Long-term”

Important distinction:

Reserved Instance ≠ automatically reserved physical capacity.

It is primarily a billing commitment.

C. Savings Plans

Why they exist

Provide discounted compute usage in exchange for a commitment.

Useful when you want more flexibility than traditional Reserved Instances.

Main categories include:

Compute Savings Plans

EC2 Instance Savings Plans

SageMaker Savings Plans

Exam thinking:

Need flexibility across:

• Instance family  
• Region  
• Operating system  
• Compute service

Compute Savings Plans are more flexible.

If workload is strongly tied to a specific EC2 configuration, EC2 Instance Savings Plans provide deeper commitment around EC2 usage.

D. Spot Instances

Why they exist

Use spare AWS capacity at significant discounts.

Problem solved

Reduce cost for workloads tolerant of interruption.

Good workloads:

• Batch processing  
• Big data  
• CI workloads  
• Stateless workers  
• Rendering  
• Image processing  
• Distributed processing

Poor workloads:

• Primary database  
• Critical single-instance application  
• Stateful application without interruption handling

Exam keyword:

“Fault tolerant”  
“Interruptible”  
“Flexible”  
“Batch”  
“Stateless workers”  
“Lowest cost”

SAP pattern:

SQS + EC2 Spot + Auto Scaling

This is a strong cost optimization architecture for asynchronous workloads.

3. DATA TRANSFER COST OPTIMIZATION
    

This is an important SAP-C02 trap.

AWS architecture is not only about compute cost.

Network architecture affects the bill.

Think:

Data movement × distance × direction × service

Potential cost areas:

• Internet data transfer  
• Cross-AZ transfer  
• Cross-Region transfer  
• NAT Gateway processing  
• Transit Gateway processing  
• Direct Connect  
• CloudFront  
• S3 data transfer  
• Inter-service communication

Most important principle

Keep high-volume traffic close to where it is consumed.

Example:

Bad:

EC2 in us-east-1  
→ Database in us-west-2

Large continuous data movement.

Better:

EC2 and database in same Region.

Similarly:

Bad:

Application in multiple AZs  
→ excessive cross-AZ traffic

Better architecture depends on workload topology.

A. NAT Gateway

NAT Gateway charges include processing costs.

If thousands of EC2 instances continuously download large files through NAT Gateway, the data processing charge becomes significant.

Possible optimization:

Use VPC endpoints for AWS services such as S3.

Architecture:

EC2  
→ S3 Gateway VPC Endpoint  
→ S3

Instead of:

EC2  
→ NAT Gateway  
→ S3

Exam clue:

“Large amount of S3 traffic from private subnets”

Think:

S3 Gateway Endpoint.

B. S3 Transfer Acceleration

Useful when:

Users are globally distributed.

Users upload large objects.

S3 bucket is far from users.

Example:

India user  
→ S3 bucket in US

S3 Transfer Acceleration routes traffic through CloudFront edge locations.

But it costs extra.

Exam thinking:

Need faster global S3 uploads  
→ Transfer Acceleration

Need lowest cost  
→ First evaluate direct S3 transfer and multipart upload.

Your previous medical imaging question is a classic example.

Large files + global upload latency  
→ Multipart Upload + S3 Transfer Acceleration.

C. CloudFront

Why it exists

Move content closer to users.

Reduces:

• Latency  
• Origin load  
• Repeated origin data transfer

Excellent for:

• Static content  
• Videos  
• Images  
• Downloads  
• APIs with suitable caching

Exam clue:

“Millions of users repeatedly download the same content”

Think:

CloudFront caching.

D. S3 Gateway Endpoint

Why it exists

Private connectivity from VPC to S3 without NAT Gateway or Internet Gateway.

Cost advantage:

Gateway endpoints have no hourly endpoint charge.

Excellent exam answer when:

Private EC2  
→ S3  
→ high volume

Think:

S3 Gateway Endpoint.

E. Interface VPC Endpoint

Uses AWS PrivateLink.

Useful for:

Private access to supported AWS services.

Trade-off:

Interface endpoints have hourly and data-processing charges.

Therefore:

Do not automatically choose Interface Endpoint when Gateway Endpoint fits.

Exam clue:

“S3 or DynamoDB from VPC”

Think Gateway Endpoint.

“Private access to supported service using PrivateLink”

Think Interface Endpoint.

4. DEVELOPING EXPENDITURE AND USAGE AWARENESS
    

This means:

“Know where money is being spent before the bill arrives.”

AWS services:

• AWS Cost Explorer  
• AWS Budgets  
• AWS Cost and Usage Report  
• Cost Categories  
• AWS Organizations  
• Service Control Policies  
• Trusted Advisor  
• CloudWatch  
• Billing Console

A. Cost Explorer

Purpose:

Analyze historical and current AWS spending.

Use it to answer:

Which service costs the most?

Which Region costs the most?

Which account increased spending?

What caused the increase?

Exam keyword:

“Analyze spending”  
“Cost trends”  
“Historical cost”  
“Usage analysis”

B. AWS Budgets

Purpose:

Set spending or usage thresholds.

Example:

Monthly budget = $10,000

Alert at:

80%  
90%  
100%

Important:

Budget alerts notify you.

They do not automatically stop all AWS resources.

Exam trap:

“Alert when spending exceeds threshold”

→ AWS Budgets.

C. Cost and Usage Report

CUR provides detailed AWS billing and usage information.

Think:

Detailed billing data  
→ CUR

Cost analysis  
→ Cost Explorer

Budget threshold  
→ AWS Budgets

D. Cost Categories

Useful for organizing costs.

Example:

Engineering  
→ Development  
→ Production

Or:

Business unit A  
Business unit B  
Business unit C

Useful in multi-account organizations.

E. AWS Organizations

Centralized account management.

Cost optimization use:

Consolidated billing.

Multiple accounts can share consolidated billing benefits.

Example:

Account A  
Account B  
Account C  
→ AWS Organizations  
→ Consolidated billing

Exam clue:

“Multiple AWS accounts”  
“Centralized billing”  
“Enterprise”

Think:

AWS Organizations.

6. SERVICE QUOTAS AND COST
    

Service limits sometimes create unexpected architecture problems.

Example:

You need:

10,000 EC2 instances.

Current quota:

5,000.

Options:

Request quota increase.

Or redesign architecture.

Do not blindly request unlimited increases.

SAP exam thinking:

Quota limit  
→ AWS Service Quotas

Quota approaching  
→ CloudWatch / Trusted Advisor where supported

Need governance  
→ Organizations / SCP

7. MANAGED SERVICES AND COST
    

Managed services often reduce operational cost.

Example:

Self-managed MySQL on EC2:

EC2  
+  
OS patching  
+  
DB patching  
+  
Backups  
+  
Replication  
+  
Monitoring  
+  
Failover

Managed:

RDS

AWS manages much of the underlying infrastructure.

But:

Managed service ≠ automatically cheaper.

You pay for managed capabilities.

SAP exam decision:

If requirement says:

“Minimize operational overhead”

Prefer managed service.

If requirement says:

“Minimize infrastructure cost at all costs”

Evaluate the actual workload and alternatives.

Do not blindly choose managed services based only on the word “managed”.

8. COST OPTIMIZATION DECISION TREE
    

Start with workload.

Is resource oversized?

→ Right-size.

Is workload variable?

→ Auto Scaling.

Is workload predictable and long-running?

→ Savings Plans / Reserved Instances.

Is workload interruptible?

→ Spot.

Is content repeatedly accessed globally?

→ CloudFront.

Is high-volume traffic going through NAT to S3?

→ S3 Gateway Endpoint.

Is data moving between Regions?

→ Reconsider architecture and data locality.

Are users globally uploading large objects?

→ Multipart Upload / S3 Transfer Acceleration based on performance requirement.

Multiple AWS accounts?

→ Organizations + consolidated billing.

Need spending analysis?

→ Cost Explorer.

Need spending alerts?

→ AWS Budgets.

Need detailed billing data?

→ Cost and Usage Report.

9. COST OPTIMIZATION VS PERFORMANCE
    

SAP-C02 often creates a conflict:

“Lowest cost”

versus

“Highest performance”

You must satisfy the business requirement first.

Example:

Global users upload 1 GB files.

Option A:

Direct S3 upload

Lowest cost.

Option B:

S3 Transfer Acceleration

Higher cost.

If requirement says:

“Improve upload performance globally”

→ S3 Transfer Acceleration.

If requirement says:

“Lowest possible cost”

→ Avoid acceleration unless measurements justify it.

This distinction is important.

10. COST OPTIMIZATION VS RELIABILITY
    

Do not sacrifice required availability to reduce cost.

Example:

Single EC2 instance:

Low cost  
Low availability

Multi-AZ:

Higher cost  
Higher availability

If SLA is 99.99%:

Do not select a single instance simply because it is cheaper.

SAP principle:

Optimize within the business requirements.

Not:

“Choose the cheapest AWS service.”

11. COST OPTIMIZATION VS OPERATIONAL OVERHEAD
    

Consider Total Cost of Ownership.

Example:

Self-managed database:

Infrastructure cost ↓

Operational effort ↑

Managed database:

Infrastructure cost ↑

Operational effort ↓

If the question says:

“Minimize operational overhead”

→ RDS / Aurora.

If it says:

“Full OS control”

→ EC2.

If it says:

“Lowest operational overhead and automatic scaling”

→ Serverless or managed services.

14. MOST IMPORTANT SAP-C02 MENTAL MODEL
    

When you see a cost question, think in this order:

1. Do I need the capacity?  
    → Right-size.
    
2. Does demand change?  
    → Auto Scaling.
    
3. Is usage predictable?  
    → Savings Plans / RI.
    
4. Is workload interruptible?  
    → Spot.
    
5. Is data moving unnecessarily?  
    → Redesign data path.
    
6. Is traffic going through an expensive component?  
    → Check NAT Gateway, Transit Gateway, cross-AZ and cross-Region transfer.
    
7. Is content repeatedly delivered?  
    → CloudFront.
    
8. Is S3 access coming from private subnets?  
    → Gateway Endpoint.
    
9. Is global S3 transfer slow?  
    → Multipart Upload / Transfer Acceleration.
    
10. Do I know where the money goes?  
    → Cost Explorer / CUR.
    
11. Do I need alerts?  
    → AWS Budgets.
    
12. Do I need organization-wide governance?  
    → AWS Organizations.
    
13. Is the architecture operationally expensive?  
    → Consider managed/serverless services.
    
14. THE BIG SAP-C02 TRAP
    

The cheapest individual service is not always the cheapest architecture.

Example:

EC2 + self-managed database

might have lower infrastructure pricing than Aurora.

But:

DBA effort  
+  
patching  
+  
backup  
+  
replication  
+  
failover  
+  
monitoring  
+  
engineering time

increase TCO.

SAP-C02 expects you to optimize:

Infrastructure cost  
+  
Data transfer cost  
+  
Operational cost  
+  
Engineering cost  
+  
Licensing cost  
+  
Failure cost

while still satisfying:

Performance  
+  
Availability  
+  
Security  
+  
Scalability  
+  
Business requirements.

Final exam rule

Cost optimization does not mean “choose the cheapest service.”

It means:

“Choose the architecture with the lowest appropriate Total Cost of Ownership while satisfying the required performance, reliability, security, scalability, and business constraints.”

For SAP-C02, this distinction is one of the most important ways to eliminate attractive but incorrect answers.
