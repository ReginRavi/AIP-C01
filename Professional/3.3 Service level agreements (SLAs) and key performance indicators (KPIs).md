Task 3.3: Determine a strategy to improve performance

Knowledge of: Service Level Agreements (SLAs) and Key Performance Indicators (KPIs)

Think like an AWS Solutions Architect Professional:

The key exam idea is:

SLA = What level of service the business promises to customers.

KPI = What measurable number tells you whether the system is performing as required.

A Solutions Architect does not optimize infrastructure first. Start with the business requirement, convert it into measurable KPIs, then design the architecture around those targets.

1. Why do SLA and KPI exist?
    

SLA exists to define the customer-facing service commitment.

Example:

Application SLA = 99.99% availability.

This means the business accepts roughly 52.6 minutes of unavailability per year.

KPI exists to measure system behavior.

Examples:

• API latency < 200 ms at p95  
• Error rate < 0.1%  
• Throughput > 10,000 requests/sec  
• Availability > 99.99%  
• Database CPU < 70%  
• Queue backlog < 1,000 messages  
• Checkout success rate > 99.9%

Think:

SLA = commitment

KPI = measurement

CloudWatch = measurement mechanism

Architecture = mechanism used to achieve the target

2. SLA vs KPI vs SLI vs SLO
    

This distinction is important for SAP exam questions.

SLA

Business agreement with the customer.

Example:

"The service will provide 99.99% availability."

SLO

Internal target used to meet the SLA.

Example:

"Engineering targets 99.995% availability."

SLI

Actual measurement of the service.

Example:

Availability = successful requests / total requests.

KPI

Business or operational metric used to measure performance.

Example:

Checkout conversion rate, API latency, requests/sec.

A useful mental model:

SLI → measurement

SLO → engineering target

SLA → contractual/business commitment

KPI → important business/operational indicator

3. What problem does SLA solve?
    

SLA establishes the expected service level.

It forces architectural decisions.

Example:

Requirement:

99.99% availability.

You should immediately think:

• Single EC2 instance is insufficient  
• Single AZ is insufficient  
• Multi-AZ architecture  
• Auto Scaling  
• Load balancing  
• Database high availability  
• Automated recovery  
• Monitoring  
• Health checks  
• Failover

If the requirement becomes:

99.999% availability

You start evaluating:

• Multi-Region  
• Route 53  
• Global Accelerator  
• Regional failover  
• Replicated databases  
• Disaster recovery  
• Automated recovery

4. What problem does KPI solve?
    

KPI tells you whether the architecture is achieving the required outcome.

Example:

Requirement:

API response time < 300 ms.

Possible KPIs:

• p50 latency  
• p95 latency  
• p99 latency  
• error rate  
• throughput  
• CPU utilization  
• database latency

Suppose:

p50 = 100 ms  
p95 = 250 ms  
p99 = 1.2 seconds

The average might look good, while 1% of users experience poor performance.

For performance questions, p95 and p99 are often more meaningful than average latency.

5. Operational overhead
    

SLA/KPI themselves are not infrastructure services.

The overhead comes from implementing measurement and enforcement.

Typical components:

CloudWatch  
CloudWatch Logs  
CloudWatch Metrics  
CloudWatch Alarms  
X-Ray  
CloudTrail  
AWS Config  
SNS  
EventBridge  
Application Performance Monitoring tools  
OpenTelemetry

The more detailed your monitoring becomes, the higher the operational and monitoring cost.

SAP principle:

Monitor what matters to the business.

Do not create thousands of unnecessary metrics and alarms.

6. Minimal requirement
    

For a basic production application:

• Define availability target  
• Define latency target  
• Define throughput target  
• Define error-rate target  
• Monitor the important metrics  
• Create alarms for SLA-impacting conditions  
• Establish escalation and remediation procedures

For example:

Availability: 99.99%

p95 latency: < 200 ms

Error rate: < 0.1%

Throughput: 5,000 requests/sec

These targets then drive architecture.

7. Cost perspective
    

Higher SLA requirements generally increase architecture cost.

Example:

99.9% availability

≈ 8 hours 46 minutes downtime/year

99.99%

≈ 52.6 minutes/year

99.999%

≈ 5.26 minutes/year

Moving from 99.9% to 99.99% requires additional resilience.

Moving from 99.99% to 99.999% often requires substantially more redundancy, automation, replication, monitoring, and operational maturity.

SAP exam principle:

Do not automatically choose the highest availability architecture.

Choose the architecture required by the business SLA.

If the requirement says:

"Cost-effective solution"

Do not immediately select multi-Region active-active.

If the requirement says:

"Near-zero downtime globally"

Multi-Region architectures become more appropriate.

Think of this chain:

10. Related AWS services
    

CloudWatch

Primary AWS monitoring service.

Use it for:

• Metrics  
• Logs  
• Alarms  
• Dashboards  
• Automated responses

CloudWatch is usually the first service to consider when the question asks for monitoring AWS resources.

CloudWatch Application Signals

Useful for application-level SLOs and application performance monitoring.

AWS X-Ray

Distributed tracing.

Useful when the problem involves:

"Which downstream service is causing latency?"

Example:

API Gateway  
→ Lambda  
→ DynamoDB  
→ external API

X-Ray helps identify where latency occurs.

CloudTrail

API activity and auditing.

Think:

"Who changed what?"

Not primarily application performance monitoring.

AWS Config

Resource configuration and compliance.

Think:

"Is the resource configured according to policy?"

Route 53 health checks

Useful for endpoint health and DNS failover.

Global Accelerator

Useful when performance and global traffic routing are involved.

CloudFront

Useful for reducing latency for globally distributed content.

11. Why CloudWatch over other services?
    

If the question asks:

"Monitor EC2 CPU utilization"

Think CloudWatch.

"Create an alarm when CPU exceeds 80%"

Think CloudWatch Alarm.

"Monitor application logs"

Think CloudWatch Logs.

"Create dashboard"

Think CloudWatch Dashboard.

"Trigger automated action based on metric"

Think CloudWatch Alarm + SNS/EventBridge/Auto Scaling.

If the question asks:

"Trace a request across multiple microservices"

Think X-Ray or OpenTelemetry-based tracing.

If the question asks:

"Who made an AWS API call?"

Think CloudTrail.

If the question asks:

"Detect configuration drift"

Think AWS Config.

If the question asks:

"Route users to healthy/lowest-latency Region"

Think Route 53.

12. SLA and autoscaling
    

Suppose KPI:

API latency must remain below 200 ms.

CPU reaches 80%.

You don't automatically scale because CPU is high.

Ask:

Is CPU correlated with the actual performance problem?

If yes:

CloudWatch metric  
→ alarm/target tracking  
→ Auto Scaling  
→ additional capacity

For queue-based systems:

Queue depth  
→ scaling policy  
→ additional workers

This is a common SAP design pattern.

The business KPI should influence the scaling metric.

13. SLA and caching
    

Requirement:

High read traffic and low latency.

Possible architecture:

CloudFront  
→ API Gateway  
→ application  
→ database

Or:

Application  
→ ElastiCache

Caching reduces database load and improves response time.

But caching introduces:

• Cache invalidation complexity  
• Stale data  
• Additional cost  
• Cache consistency concerns

Exam principle:

Use caching when the workload has repeated reads and latency matters.

14. SLA and database replicas
    

Requirement:

High read throughput.

Possible solution:

RDS read replicas.

Requirement:

High availability.

Possible solution:

RDS Multi-AZ.

Important distinction:

Read Replica → read scalability

Multi-AZ → high availability/failover

Aurora replicas → read scalability and availability

Aurora Global Database → cross-Region disaster recovery and global reads

15. SLA and RTO/RPO
    

These concepts connect directly.

SLA:

"Service availability must be 99.99%."

RTO:

"Application must recover within 5 minutes."

RPO:

"Maximum acceptable data loss is 1 minute."

These requirements determine:

• Backup strategy  
• Replication  
• Multi-AZ  
• Multi-Region  
• Failover automation  
• Database technology

16. SLA does not mean 100% availability
    

AWS services themselves have defined SLAs.

Your application SLA depends on the entire architecture.

Example:

EC2 SLA alone does not make your application 99.99% available.

You need to consider:

EC2  
+  
AZ  
+  
ALB  
+  
database  
+  
network  
+  
application  
+  
DNS  
+  
deployment process

The weakest dependency might become the availability bottleneck.

18. SAP exam decision framework
    

When you see an SLA/KPI question, follow this order:

1. Identify the business requirement.
    
2. Convert it into a measurable target.
    
3. Identify the bottleneck.
    
4. Select the correct metric.
    
5. Select the architecture required to meet the target.
    
6. Add monitoring.
    
7. Add automated remediation where appropriate.
    
8. Evaluate cost.
    
9. Avoid overengineering.
    

The key mental model for the exam is:

SLA tells you how good the service must be.

KPI tells you what to measure.

SLI tells you the actual observed performance.

SLO tells engineering the target.

CloudWatch measures the system.

Architecture determines whether the target is achievable.

Cost determines how far you should go beyond the minimum required target.
